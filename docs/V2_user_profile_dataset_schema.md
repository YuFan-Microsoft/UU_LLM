# V2 User Profile Dataset: Input and Output Schemas

This guide covers the 8 `V2_*` configs in
[`yufan/user_profile_dataset`](https://huggingface.co/datasets/yufan/user_profile_dataset).
The training responses were generated by GPT-5.6.

Each task shows what the model reads and what it returns. The notes explain which fields are optional, how
missing data is represented, and what to watch for when reading the data.

## 1. Dataset overview

| Config | Task | Train | Test |
|---|---|---:|---:|
| `V2_User_Profile_L1_gpt56` | Raw activities → interests | 267,810 | 5,378 |
| `V2_User_Profile_L1_Negative_gpt56` | Negative feedback → rejected topics | 557,734 | 11,184 |
| `V2_User_Profile_L2_gpt56` | Existing profile + new interests → merge / add decisions | 259,918 | 5,199 |
| `V2_User_Profile_L3_Commercial_gpt56` | Interests → commercial label, brands, search queries | 145,277 | 7,059 |
| `V2_User_Profile_L3_Persona_gpt56` | Interests → persona + category | 77,312 | 3,780 |
| `V2_User_Profile_L4_Biography_gpt56` | Interests + facts → life stage, attributes, biography | 161,793 | 8,103 |
| `V2_User_Profile_L4_CommercialPreference_gpt56` | Commercial interests → shopping preferences | 141,250 | 7,093 |
| `V2_User_Profile_L4_Hyper_gpt56` | Commercial interests + context → ad missions + new queries | 94,514 | 4,843 |

The [appendix](#appendix-missing-and-empty-input-fields) gives the missing-field and empty-value counts for each
config. It distinguishes a missing key from a key whose value is `{}`, `[]`, or `""`.

## 2. What each row contains

All configs use the same outer row format:

```ts
{
  uid: string,             // 16-char hex user ID (L1 Negative: hash of the row's actions, the data has no user ID)
  messages: [
    { role: "user",      content: PROMPT + "\n\nInput:\n" + INPUT },
    { role: "assistant", content: OUTPUT }          // minimized JSON
  ],
  source: "GPT56",
  domain: string,          // see the table below
  think_type: "none",
  language?: string        // see the table below
}
```

Each row has one user message followed by one assistant message, with no system message. All rows in a config
use the same prompt. The assistant's response is a JSON string that can be read with `json.loads`.

Use the following code to separate the prompt, input, and output:

```python
import json

prompt, _, raw_input = row["messages"][0]["content"].rpartition("\nInput:\n")
output = json.loads(row["messages"][1]["content"])
if row["domain"] in ("maiprofile-layer1-combined", "maiprofile-layer1-negative"):  # JSONL: one object per line
    input_data = [json.loads(line) for line in raw_input.split("\n")]
else:
    input_data = json.loads(raw_input)
```

| Config | `domain` | `language` column | Input format |
|---|---|---|---|
| L1 | `maiprofile-layer1-combined` | content language (= output `predicted_content_locale`) | JSONL |
| L1 Negative | `maiprofile-layer1-negative` | market: `en` or `glb` | JSONL |
| L2 | `maiprofile-layer2-combined` | *(no column)* | JSON |
| L3 Commercial | `maiprofile-layer3-commercial` | input `query_language` | JSON |
| L3 Persona | `maiprofile-layer3-persona` | always `en` | JSON |
| L4 Biography | `maiprofile-layer4-biography` | always `en` | JSON |
| L4 Commercial Preference | `maiprofile-layer4-commercial-preference` | always `en` | JSON |
| L4 Hyper | `maiprofile-layer4-hyper` | input `query_language` | JSON |

## 3. How the tasks fit together

L1 extracts interests from activity history. L2 merges new interests into an existing profile. L3 adds persona
and commercial information, which the L4 tasks use to build a biography, shopping preferences, and ad missions.
L1 Negative is separate because its records do not have user IDs that can be joined to the other tasks.

```
L1  raw activities -> interests
 `-- L2  merge new interests into the user's profile
      |-- L3 Persona       persona + category for each interest
      `-- L3 Commercial    commercial label, brands, queries for each interest
           `-- L4 Biography                  life stage, user attributes, biography
                `-- L4 Commercial Preference  shopping preferences
                     `-- L4 Hyper              ad missions + new queries

L1 Negative  negative feedback -> rejected topics   (standalone: no user ID to join with the other layers)
```

## 4. Reading the schemas

The schemas below use these shared types:

```ts
// Source: activity source. The 9 values after "Shopping" are rare (259 occurrences, only in L3 Commercial / L4
// Biography inputs; "Home Depot" 6)
type Source = "MSN" | "Edge" | "Uet" | "Bing" | "Ads" | "ChromeImports" | "Shopping" | "Linkedin"
            | "YouTube" | "Amazon" | "Xbox" | "Facebook" | "Google Play" | "Walmart" | "Yahoo" | "Home Depot";
type Lang   = "en" | "de" | "fr" | "es" | "ja" | "pt" | "nl" | "it" | "sv" | "pl" | "zh-Hans" | "zh-Hant";
type Level  = "high" | "medium" | "low";
type Scale  = "Low" | "Medium-Low" | "Medium" | "Medium-High" | "High";
type Signal = "strong" | "moderate" | "weak";
```

In a schema, `field?` means the field is optional. A comment such as `~N%` tells you how often it is present.
Counts such as `1–39, median 10` describe the data we measured, not necessarily a limit imposed by the prompt.
All counts and percentages cover the full config, including train and test.

## L1: Interest extraction

Config: `V2_User_Profile_L1_gpt56`

The model reads a window of activities and extracts the user's interests.

**Input**

The input is JSONL, with one activity per line. A row contains 1–200 activities, with a median of 37.

```ts
{ idx: int, date: "YYYY-MM-DD", source: Source, action: string }   // action: page title, query, or article title
```

**Output**

```ts
{
  predicted_content_locale: Lang | "mix",   // main language of the activities
  interests: [{                             // 0–39, median 10 (0.3% of rows have none)
    interest_name: string,
    topics: [{                              // 1–53, median 2
      topic: string,
      source: Source[],                     // 1–6
      evidence: int[]                       // input idx
    }],
    actual_activity: string,                // one factual sentence
    inferred_intent: string                 // the intent one step above the activity
  }]
}
```

## L1 Negative: Rejected topics

Config: `V2_User_Profile_L1_Negative_gpt56`

The model reads a batch of negative feedback and identifies the topics the user wants to avoid.

**Input**

The input is JSONL, with one feedback signal per line and no dates. A row contains 1–148 signals, with a median
of 1. Most rows (74%) contain just one signal.

```ts
{
  idx: int,                       // 0..n-1
  source: "MSN" | "Ads",
  detailed_source: "ContentUserFeedback" | "AdUserFeedback",
  action: string                  // MSN: "Downvote | <content title>"
                                  // Ads: "NotInterested | <advertiser> | <ad title>"
}
```

**Output**

```ts
{
  negative_interests: [{          // 1–103, median 1
    keywords: string,             // the rejected topic: 1–8 lowercase words (median 4), any language
    evidence: int[],              // input idx it is based on (95% cite one signal)
    source: ("MSN" | "Ads")[],    // sources of the cited signals
    detailed_source: string,      // detailed source of the cited signals
    signal_type: string[],        // lowercase action prefixes: "downvote" | "notinterested"
    reliability_score: float      // 0–1 (observed 0.72–0.99, median 0.96)
  }]
}
```

Every input signal is cited by at least one negative interest.

For MSN feedback, the source fields are `MSN` and `ContentUserFeedback`, and the signal type is `downvote`.
For ads, they are `Ads`, `AdUserFeedback`, and `notinterested`. One interest has the combined `signal_type`
`"repeatedad~inappropriatead~notinterested"`.

The `keywords` field describes the rejected topic, not the reaction. For example, "offensive" is a reaction,
not a topic. In the dataset, 94% of keyword strings are plain ASCII, mostly English.

## L2: Profile merge

Config: `V2_User_Profile_L2_gpt56`

For each new interest, the model decides whether to merge it into an existing interest or add it to the profile.

**Input**

```ts
{
  // existing profile, 0–275 interests (median 39)
  snapshot: [{ interest_name: string, actual_activity: string, topics: string[] }],
  // new interests, 1–95 (median 10)
  delta:    [{ interest_name: string, actual_activity: string, topics: string[] }]
}
```

**Output**

Return one decision for each interest in `delta`, in the same order as the input.

```ts
{
  decisions: [
      { action: "merge",                     // ~60%
        delta_interest_name: string, snapshot_interest_name: string,
        merged_interest_name: string, merged_actual_activity: string, merged_inferred_intent: string }
    | { action: "add",                       // ~40%
        delta_interest_name: string, actual_activity: string, inferred_intent: string }
  ]
}
```

## L3 Commercial: Commercial classification

Config: `V2_User_Profile_L3_Commercial_gpt56`

For each interest, the model decides whether it is relevant to advertisers. It also lists brands, retailers,
products, and possible search queries.

**Input**

```ts
{
  interests: [{                              // 1–30, median 24
    interest_name: string,
    actual_activity: string,
    sources: Source[],
    topics: [{ topic: string, actions: string[] }]   // actions: raw activity texts (0–3)
  }],
  query_language: Lang
}
```

**Output**

Return one entry for each input interest.

```ts
{
  interest_commercial: [{
    interest_name: string,
    commercial: boolean,                                       // true ~75%
    commercial_score: "high" | "medium" | "low" | null,
    intent_funnel_stage: "discovery" | "research" | "consideration" | "purchase" | "post-purchase" | null,
    brands: string[],
    retailers: string[],
    products: string[],
    predicted_queries: string[]                                // ≤ 3, in query_language
  }]
}
```

When `commercial` is `false`, both `commercial_score` and `intent_funnel_stage` are `null`, and all list fields
are empty arrays (`[]`).

## L3 Persona: Interest personas

Config: `V2_User_Profile_L3_Persona_gpt56`

For each interest, the model describes the user's motivations and behavior and assigns a category path.

**Input**

```ts
{
  interests: [{                 // 1–229, median 42
    interest_name: string,
    actual_activity: string,
    inferred_intent: string,
    topics: string[]
  }]
}
```

**Output**

Return one entry for each input interest.

```ts
{
  interest_personas: [{
    interest_name: string,
    category: string,           // "/" path, broad → specific,
                                //   e.g. "/Technology/Artificial Intelligence/AI Assistants"
    persona: string
  }]
}
```

## L4 Biography: User attributes and biography

Config: `V2_User_Profile_L4_Biography_gpt56`

The model uses interests, facts, and declared attributes to infer the user's life stage and other attributes,
then writes a short biography.

This config has 169,896 rows from 20,861 users. The train split has 19,873 users and the test split has 988,
with no users shared between the two splits.

We removed `user_attributes.age_group.signals` from the GPT-5.6 output. That field was present in 115,429 rows
(67.9%), covering every row without a declared `age_group`. No other Biography output fields were changed.

**Input**

```ts
{
  declared_attributes: {                     // {} in 65% of rows
    age_group?: "18 - 24" | "25 - 34" | "35 - 49" | "50 - 65" | "65+",   // ~32%
    gender?: "Male" | "Female"                                           // ~26%
  },
  facts: {                                   // {} in 55% of rows
    market?: string,                         // ~28%, e.g. "en-US"
    location_data?: {                        // ~30%
      current_location: string,
      place_frequency:  [{ place: string,  count: int }],
      region_frequency?: [{ region: string, count: int }],   // ~97% of location_data
      recent_visits?: string[]                               // ~53% of location_data
    },
    linkedin_profile?: {                     // ~16%; sparse fields, each a string or string[]
      profile_geo?: string,                  // 99.9% of linkedin_profile
      industries?, degree?, degrees?, fieldOfStudy?, areas?, titles?, current_roles?,
      yearsOfExperience?, experience_band?, seniorities?, functions?, companies?, current_company?
    }
  },
  interests: [{                              // 1–203, median 41
    interest_name: string,
    actual_activity: string,
    inferred_intent: string,
    persona: string,                         // from L3 Persona
    confidence_score: float,
    count: int,
    first_detect_date: "YYYY-MM-DD",
    last_detect_date: "YYYY-MM-DD",
    source: Source[],
    topics?: string[],                       // missing for 4 interests (4 rows)
    predicted_queries?: string[],            // ~68%, from L3 Commercial
    products?: string[],                     // ~51%
    brands?: string[]                        // ~44%
  }]
}
```

**Output**

```ts
type AttrSource = "declared" | "behavioral_inference" | "location_data" | "linkedin" | "unknown";
type Attr = { evidence: string[], value: string, confidence: Level, source: AttrSource };

{
  life_stage: {
    value: "single" | "married" | "parenting" | "caregiving" | "job_seeking" | "new_grad" | "retirement"
         | "unknown",
    confidence: Level,
    evidence: string[]                       // 1–3
  },
  user_attributes: {                         // always all 8 keys, in this order
    age_group: Attr,                         // "13 - 17" | "18 - 24" | "25 - 34" | "35 - 49" | "50 - 65" | "65+"
                                             //   | "Unknown"
    gender: Attr & { lean: { male: string[], female: string[] } },   // "Male" | "Female" | "Unknown"
    estimated_income_level: Attr,            // "High" | "Medium" | "Low" | "Unknown"
    home_location: Attr,                     // place name | "Unknown"
    occupation: Attr,                        // occupation category | "Unknown"
    company: Attr,                           // company name | "Self-Employed" | "Unknown"
    career_stage: Attr,                      // "Student" | "Entry Level" | "Mid-Level Professional"
                                             //   | "Senior Professional" | "Manager" | "Director/Executive"
                                             //   | "Business Owner/Self-Employed" | "Retired"
                                             //   | "Not in Workforce" | "Unknown"
    education_area: Attr                     // field of study | "Unknown"
  },
  biography: string                          // 2–3 sentences, 143–550 chars (median 323)
}
```

The stored JSON uses a fixed key order. Each `Attr` is written as `{evidence, value, confidence, source}`.
For `gender`, the order is `{lean, evidence, value, confidence, source}`.

**How to read the attributes**

An unknown attribute always has `value: "Unknown"`, `source: "unknown"`, and `evidence: []`. These three values
occur together in every row. A known attribute has 1–3 evidence items.

Declared attributes are copied without changes. All 54,467 rows with a declared `age_group` return that value
with `source: "declared"`. The same is true for the 44,399 rows with a declared gender.

The `gender.lean` object always contains `male` and `female`, with 0–10 entries in each list. When gender is
inferred, entries have the form `"<interest name> (strong|moderate|weak)"`, such as `"Football (moderate)"`.
Across these entries, 51.0% are weak, 44.0% moderate, and 4.9% strong. When gender is declared, the lists are not
scored: they contain one free-text entry such as `"Declared male"` in 43,260 rows, or are both empty in 1,139 rows.

Although `age_group.signals` was removed, the evidence text was left as it was. As a result, 25,076 rows (14.8%)
still mention "later-life", for example `"... provide two later-life clusters"`.

## L4 Commercial Preference: Shopping preferences

Config: `V2_User_Profile_L4_CommercialPreference_gpt56`

The model summarizes how the user shops, including sensitivity to price and discounts, subscription preferences,
shopping categories, and dietary restrictions.

**Input**

```ts
{
  life_stage: { value: string, confidence: Level, evidence: string[] },   // L4 Biography output
  commercial_interests: [{                   // 1–119, median 27
    interest_name: string,
    persona: string,
    brands: string[],
    retailers: string[],
    products: string[],
    topics: [{ topic: string, evidence: string[] }]   // evidence: raw activity texts
  }],
  non_commercial_interest_names: string[]
}
```

**Output**

```ts
type Detail<K extends string, V> = { area: string, evidence: string, signal_strength: Signal } & { [key in K]: V };

{
  discount_sensitivity:  { value: Scale | "Unknown", details: Detail<"sensitivity", Scale>[] },
  price_sensitivity:     { value: Scale | "Unknown", details: Detail<"sensitivity", Scale>[] },
  subscription_affinity: { value: Scale | "Unknown", details: Detail<"affinity", Scale>[] },
  affinity: {
    shopping: {
      product_categories: [{ category: AdsVertical, description: string }],
      shopper_type: { value: ShopperType[], details: Detail<"type", ShopperType>[] }
    },
    dining: {
      restrictions: { value: Diet[], details: Detail<"restriction", Diet>[] }   // value ["Unknown"] when no signal
    }
  }
}

type AdsVertical = "HomeGarden" | "ComputersConsumerElectronics" | "RetailersGeneralMerchandise" | "TravelTourism"
                 | "Finance" | "Apparel" | "Vehicles" | "InternetTelecom" | "Health" | "BeautyPersonalCare"
                 | "SportsFitness";          // Ads Vertical L1
type ShopperType = "ResearchDriven" | "DealDriven" | "BrandRetailerLoyal" | "ValueDriven"
                 | "NoveltySeeker" | "ConvenienceDriven" | "PremiumDriven"
                 | "ImpulseDriven";          // ImpulseDriven: 1 row
type Diet        = "Unknown" | "Vegan" | "Vegetarian" | "No Gluten" | "Low-Carb" | "Keto" | "Halal" | "Dairy-Free"
                 | "Kosher" | "Pescatarian" | "Paleo" | "No Nuts"
                 | "No Shellfish";           // the last 5 are rare (166 occurrences; No Shellfish 2)
```

When a `value` is `"Unknown"`, the corresponding `details` list is empty (`[]`).

## L4 Hyper: Ad missions and queries

Config: `V2_User_Profile_L4_Hyper_gpt56`

The model groups commercial interests into goals, called missions, and writes new search queries for ad
retrieval. Each mission names the interests it came from.

**Input**

The input is a JSON object. Its first four fields are strings, even when they contain JSON or Markdown.

```ts
{
  personal_context: string,        // Markdown list or "": Market, Current location, Age group, Gender,
                                   //   Recent visits
  professional_context: string,    // Markdown list, "" in ~88%: Current company, Current roles, Functions,
                                   //   Industries, Seniorities, Years of experience, Degrees, Education areas
  commercial_preferences: string,  // a JSON string: parse it again (format below)
  commercial_interests: string,    // Markdown, one block per interest (format below)
  query_language: Lang
}
```

Parse the `commercial_preferences` string again to get the object below. It is a shorter version of the
L4 Commercial Preference output, with `confidence_score` in place of `details`.

```ts
{
  discount_sensitivity?:  { value: Scale, confidence_score: float },
  price_sensitivity?:     { value: Scale, confidence_score: float },
  subscription_affinity?: { value: Scale, confidence_score: float },
  affinity?: {                                   // missing in 2 rows
    shopping: {
      product_categories?: [{ category: string, description: string }],   // missing in 4 rows
      shopper_type?: { value: ShopperType[], confidence_score: float }
    },
    // Diet plus "Low-Purine" / "Low-Sodium" (1 row each)
    dining?: { restrictions: { value: Diet[], confidence_score: float } }
  }
}
```

The `commercial_interests` string contains one Markdown block per interest, using the format below.
In fewer than 0.1% of rows, a block is missing its Category, Persona, Activity, or Intent line.

```md
### Interest 1: <interest_name>
- Category: /A/B/C
- Persona: ...
- Activity: ...
- Intent: ...
- Existing queries:
  - <query>
- Known entities:          (optional)
  - Brands: a, b
  - Retailers: a, b
  - Products: a, b
```

**Output**

```ts
{
  missions: [{                                   // 0–17, median 12 (128 rows have none)
    mission_name: string,                        // in query_language
    source_interests: string[],                  // exact input interest names
    scenarios: ("shopping" | "travel" | "technology" | "hobbies" | "learning" | "fitness" | "dining")[],
    predicted_brands: string[],                  // ≤ 3 new brands
    predicted_queries: string[]                  // observed: 1–4 queries, each 1–8 words (median 4), in query_language
  }]
}
```

**Output statistics** (99,357 rows, 1,016,271 missions, 2,213,233 queries)

A row contains 0–17 missions, with a mean of 10.2 and a median of 12. Each mission has 1–4 queries, with a mean
of 2.18 and a median of 2.

A mission can have several scenarios. The share tagged with each scenario is: shopping 81.3%, travel 19.2%,
technology 15.5%, hobbies 12.1%, learning 6.6%, fitness 3.7%, and dining 2.9%.

Most missions predict no new brands: 74.4% have 0, 16.6% have 1, 5.7% have 2, and 3.2% have 3.

Using the Qwen3.5-4B chat template with thinking disabled, full chat length has a mean of 6,414 tokens,
P50 of 5,879, P90 of 11,846, P99 of 15,026, and a maximum of 17,511.

**Changes to the output format and prompt**

Each query is now a plain string. The old per-query fields `value_type`, `source_query_refs`, `delta_source`,
`delta_evidence`, and `decision_change`, along with the per-mission `enrichment_sources` field, were removed from
every row. This covered 2,213,233 queries in 1,016,271 missions, reduced output characters by 74%, and lowered mean
full chat length from 8,137 to 6,414 tokens.

The prompt now asks for a list of query strings, without labels, citations, or `enrichment_sources`. It does not
set a numeric limit on query count or word length. The counts above describe the existing data, not prompt
requirements. Removing the count and word-length instructions changed only the prompt, not the inputs or outputs.
The token-length statistics were measured before that prompt-only change.

## Appendix: Missing and empty input fields

This section summarizes a scan of all 43 V2 files, covering 1,758,247 train and test rows. For each input field,
we counted missing keys separately from keys with an empty value (`{}`, `[]`, or `""`). For L4 Hyper, we also
parsed the JSON strings and checked each line of the Markdown fields.

Every row can be parsed, contains one `user` message followed by one `assistant` message, and uses its config's
prompt. No V2 input contains `null`. In the tables below, "rare" means fewer than 0.5% of the rows or items
being counted.

### A.1 How each config represents missing data

| Config | Rows | Top-level keys (always all present) | Top-level value can be empty | Absent optional data inside |
|---|---:|---|---|---|
| L4 Hyper | 99,357 | `personal_context`, `professional_context`, `commercial_preferences`, `commercial_interests`, `query_language` | `personal_context` = `""` 44.3%; `professional_context` = `""` 87.6% | **line / key omitted** inside the Markdown and JSON strings (never an empty value) |
